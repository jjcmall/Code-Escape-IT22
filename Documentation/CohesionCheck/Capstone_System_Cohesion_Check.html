Part I. Core Requirements Alignment

Core Requirement / CapabilityWho Needs It?Why It Matters
The system must present a programming question for the chosen language, check the player's answer against a stored solution, and give a hint and feedback.Player (student); instructorThis is the learning core of the game. Without answer checking, obstacles cannot unlock and nothing is taught.
The player must be able to move the character, and obstacles and hazards must block or catch the player until the related question is solved.PlayerIt links play to learning: every question is triggered by an obstacle.
The system must unlock levels in order, show them on a level map, and allow cleared levels to be replayed.Player; group (content design)It enforces the learning order and shows the player where they are in the story.
The system must calculate the player's score (points for solved challenges, a penalty for hints) and show the result.Player; instructorScores give feedback and are the data any later report or ranking would use.
The system must keep the player's progress after the game is closed and restore it when the game is opened again.Player; group (testing and demonstration)Sessions are interrupted. Without this, the player would restart the story every time.

Planned capabilities (not counted above). A login and registration system and an administrator account that can change the coding questions are planned and will be implemented later. They are not implemented yet.

Architecture explanation

The student interacts with the Unity PC client through the keyboard and mouse: menus, level map, question panel, and character movement. Main processing happens inside the client. Obstacle contact opens a question, ProgrammingChallengeManager checks the answer and updates the score, and the level managers unlock levels. Persistent data is stored locally in PlayerPrefs and copied to Unity Cloud Save, which is loaded when the game starts. Components communicate through C# events and singleton references; the client reaches Unity Authentication and Cloud Save through the Unity Gaming Services SDK. The component currently being implemented and verified is the cloud save and its status screen. The next component to implement is the Login and Registration system, because an administrator account and recoverable per-student progress both depend on it.

Part VI. Next Technical Milestone

Current GapThe game signs the player in anonymously. Progress belongs to a device and cannot be recovered on another device or after cleared data. There is no login or registration, so progress cannot be tied to a named student, and there is no way to create an administrator account.
Next Technical MilestoneImplement the Login and Registration system (milestone 1 in the Capstone Technical Design and Implementation Baseline): a Login and Registration UI connected to Unity Authentication, replacing anonymous sign-in. The sign-in method will be chosen by the group from those Unity Authentication supports.
ReasonRecoverable per-student progress, and the planned administrator account that edits questions, both depend on a signed-in identity. The cloud save and the sign-in step already exist, so this milestone adds an interface and a sign-in method without adding new technology.
Expected OutputA student can register and sign in; progress is saved and loaded under that account and is available after signing in on another device; sign-in errors are shown with a retry; the architecture diagram shows the Login UI as Implemented.
