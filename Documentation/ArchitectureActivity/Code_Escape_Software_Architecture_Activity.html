Inspected on 8 November 2026. The scripts are in Assets/Scripts.

Only two new classes were added. Every other component keeps its current job.

Test question from the activity. If the score rule changes, only ProgressRecordBuilder (and ProgrammingChallengeManager, which awards the points) should change. If the cloud provider changes, only the Unity Authentication and Cloud Save calls in CloudProgressService should change. Today the first case also touches the class that talks to the network.

Part V. Refactored Feature: Save Player Progress

Status: applied in the code, compiles in Unity, and all 8 tests passed in Play Mode (see Part VII). The "before" is the code as of 8 November 2026. The "after" is the real code now in the repository working folder (not yet committed). The tests are in Part VII; the network failure there was simulated.

1. The feature before refactoring

Saving progress is one chain inside CloudProgressService: RequestSave (debounce) → FlushAsync → SaveAsync → BuildRecord → CloudSaveService.Instance.Data.Player.SaveAsync. Loading is HandleLoadedAsync → ApplyToGame. BuildRecord contains the rules for what the record says:

// CloudProgressService.cs (actual, shortened)
void BuildRecord(out PlayerProgressData record, out ProgressSnapshot snapshot)
{
    ProgressSaveService.Instance.SaveNow();            // flush local save
    record = Record != null ? Record.Clone() : new PlayerProgressData();
    ...
    foreach (ProgrammingLanguage language in Languages)
        { var data = SaveManager.LoadLevelProgress(language); ... }   // level progress
    record.completed_levels = OrderedLevelIds(completed, levels);
    ... LevelProgressManager.Instance.IsUnlocked(...) ...            // highest unlocked
    ... ProgrammingChallengeManager.Instance.ScoredObstacleIds ...    // scored challenges
    record.total_score = Mathf.Max(0, scored * PointsPerCorrectAnswer
                                      - hints * HintPenalty);         // score rule
    UnlockAchievements(record, maxClearedInOneLanguage, levelCount);  // achievement rules
}

2. The problem with the original organization

  • The network coordinator also holds the score formula, the achievement rules and the "highest unlocked level" rule.
  • Saving and loading are mirror images (BuildRecord and ApplyToGame) but live in different parts of a very large class, so a change to one is easy to forget in the other.
  • The record builder cannot be tested without the service, the network client and every manager existing.

3. The new component organization

ProgressionUI (view: status chip, panel)
      |
CloudProgressService (coordinator: state, debounce, confirm, retry)
      |-- ProgressRecordBuilder   (game state -> PlayerProgressData + ProgressSnapshot)
      |-- ProgressSnapshotApplier (ProgressSnapshot -> game managers)
      |-- PlayerProgressData / ProgressSnapshot (model)
      '-- Unity Authentication + Cloud Save (data service, Unity packages)
  • Move, do not change. The method bodies of BuildRecord, OrderedLevelIds, UnlockAchievements and ApplyToGame move into the two new classes. The logic, the JSON written and the fingerprint stay the same, so a save made before the change is still loaded after it.
  • Same public behavior. CloudProgressService keeps its public members (RequestSave, State, SaveStatus, Changed), so ProgressionUI and the rest of the game need no change.
  • No new layers or services. Two classes, both in Cloud/.

4. Relevant code after refactoring

// CloudProgressService.cs: the service now only calls the builder and the applier
void BuildRecord(out PlayerProgressData record, out ProgressSnapshot snapshot)
{
    ProgressRecordBuilder.Build(Record, client.UserId, out record, out snapshot, out string newestAchievement);
    LastUnlockedAchievement = newestAchievement;
}

void ApplyToGame(ProgressSnapshot snapshot)
{
    applying = true;
    try { ProgressSnapshotApplier.Apply(snapshot, Record); }
    finally { applying = false; }
}

// ProgressRecordBuilder.cs: the rules, with no network, no UI, no PlayerPrefs sync flags
public static void Build(PlayerProgressData lastKnown, string playerId,
    out PlayerProgressData record, out ProgressSnapshot snapshot, out string newestAchievement)
{ ... completed levels, highest unlocked, score formula, achievements ... }

// ProgressSnapshotApplier.cs: the mirror image
public static void Apply(ProgressSnapshot snapshot, PlayerProgressData record)
{ ... language, level progress, playthrough, achievements ... }

The method bodies were moved without changing their logic. SaveAsync, RequestSave, Fingerprint and all public members of CloudProgressService are unchanged, so ProgressionUI and the rest of the game need no edits. The unused Languages field was removed from the service (the builder has its own).

Part VIII. Architecture Reflection

1. Which component had the most mixed responsibilities? CloudProgressService. It handles connection, accounts, save timing, the score rule, achievement rules and restoring data into the game.

2. Which responsibilities did we separate? Building the record (with the score and achievement rules) and restoring a snapshot into the game moved into ProgressRecordBuilder and ProgressSnapshotApplier. The service keeps only connection and save timing.

3. Which concept was most useful? Layered Architecture, together with Client-Server. They show where the rules end and the Cloud Save calls begin.

4. Which concept was not necessary? Microservices. Unity's managed Cloud Save is enough for the capstone.

5. How will this help later? A new level, score rule or achievement is changed in one small class, and a change of cloud provider only touches the Cloud Save calls.
