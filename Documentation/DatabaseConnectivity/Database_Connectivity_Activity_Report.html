Why the game stores this data. Players stop and return. Without stored progress they would repeat solved questions and levels, and the group could not show learning progress or build a score summary later.

Part III. Database Design

Unity Cloud Save stores key-value items for each signed-in player, not SQL tables. The structure is one record type, PlayerProgressData, stored as JSON text under the key code_escape_progression, plus a second key, code_escape_snapshot, for restoring the game state. Cloud Save stores each player's items under that player, so one player's data cannot overwrite another's.

Field NameData TypeDescription
player_idTextUnity Player ID of the owner (unique identifier)
versionNumberRecord format version
current_levelTextLevel ID of the level reached
highest_unlocked_levelTextLevel ID of the furthest level unlocked
completed_levelsList of textCleared level IDs, no duplicates
total_scoreNumberAccumulated score (not below 0)
achievementsList of textUnlocked achievement IDs
last_playedText (ISO date and time)When the record was last updated (UTC)
scored_challenges, penalised_hintsList of textBookkeeping so each solved challenge and hint is counted once

Mapping to the suggested player_scores fields: player_id = player_id; player_name = not stored yet; score = total_score; level = current_level; remarks = achievements and completed_levels; created_at = last_played.

[Screenshot: Unity Dashboard, Cloud Save, Player Data, showing the keys code_escape_progression and code_escape_snapshot. The group already has this screenshot.]

Purpose of the structure. It keeps each student's progress, score and achievements so the game can restore them on the next start.

Unique identifier. player_id, the authenticated Unity Player ID. Cloud Save stores the items under that player.

Fields required before saving. player_id (set from the signed-in player), version, and the level and score fields. The game fills missing lists with empty lists, clamps the score at 0 and removes duplicate or unknown level IDs before saving. A load fails, without overwriting anything, if only one of the two keys exists or the data cannot be read.

Part IV. Database Connectivity Implementation

How the connection works

On start, CloudProgressService (Assets/Scripts/Cloud) initialises Unity Gaming Services, signs in anonymously with Unity Authentication, and loads the two keys from Cloud Save. If a record exists, it is restored into the game's save system; if not, a new record is created. When progress changes, the service builds the record and saves both keys in one request. No password or key is in the code: the project is linked to a Unity Dashboard project, and Cloud Save only accepts requests from a signed-in player.

// Load (CloudProgressService.cs)
var items = await CloudSaveService.Instance.Data.Player.LoadAsync(
    new HashSet<string> { KeyProgression, KeySnapshot },
    new PlayerData.LoadOptions(new PlayerData.DefaultReadAccessClassOptions()));

// Save (CloudProgressService.cs)
await CloudSaveService.Instance.Data.Player.SaveAsync(
    new Dictionary<string, object> { { KeyProgression, recordJson }, { KeySnapshot, snapshotJson } },
    new PlayerData.SaveOptions(new PlayerData.DefaultWriteAccessClassOptions()));

Answers

What action triggers saving? Clearing a level (saved at once), unlocking a level, solving a challenge or changing the score (grouped together after 3 seconds), returning to the main menu, and the app being paused. If the data has not changed, nothing is sent.

How does the game retrieve stored data? At startup it calls Cloud Save LoadAsync for the signed-in player. Gameplay stays locked behind a "Connecting to Unity Cloud Save" screen until the load succeeds; on failure the screen shows the error and a Retry button.

Where is the retrieved data displayed? On the existing level map (cleared, available and locked levels), in the Continue panel of the main menu, and in a "Cloud progress" panel on the main menu and level map showing the Player ID, current and highest unlocked level, completed levels, total score, achievements and last update. The group should confirm the panel's appearance in the screenshot, because it was built in code and its layout was not checked on screen when this report was prepared.

Problem encountered. After the Cloud Save package was added, Unity showed a "Package Manager Error": Packages/manifest.json was not valid JSON because the line for com.unity.services.cloudsave appeared twice. Other early problems: looking for the saved data in the Dashboard's Game Data page (which is for server-written items) instead of Cloud Save, Player Data; and the Editor pausing the game while the window was in the background, which delayed saves during testing.

How it was solved. The duplicate line was removed and the file was checked as valid JSON; Unity then loaded the packages. The Player Data page was used to view the saved keys. For testing, the game was kept running in the background for that Editor session.

How this activity shows that a game application is a system of connected parts.

Code Escape is more than a game screen. A player gives input, the game logic turns it into results such as a score or an unlocked level, and those results become data. That data does not stay inside one script: an event announces it, the cloud service builds a record, the network carries the record to Unity Cloud Save, and Cloud Save keeps it under the player's identity. On the next start the same parts work backwards: authentication identifies the player, storage returns the record, the save system restores it, and the interface displays it. Each part depends on the others. If the network fails, the game cannot load and shows an error; if the data design is wrong, the level map shows the wrong levels; if the repository is missing a file, another developer cannot run it. The game is therefore a system with inputs, processes, storage, outputs and supporting tools that must fit together.

Part VIII. Group Reflection and Technical Learning

Draft based on the work done. The group should review and edit it so it reflects its own experience.

What the group achieved. The existing Code Escape game now saves progress to Unity Cloud Save and loads it when the game starts, without a login screen. The level map and a progress panel show the saved data, and the game blocks play with an error and Retry button when the cloud cannot be reached.

Technical learning.

  • Cloud Save needs a signed-in identity. Anonymous sign-in gives one without a login screen, but it cannot recover progress on another device, so a login system is planned.
  • Player data in Cloud Save is key-value JSON, not SQL tables, so the data design is a record structure rather than a table with relationships.
  • Saving should be confirmed before the game says "saved". The game shows Unsaved, Saving, Saved or Failed, and keeps the local save as a backup.
  • Repeated events can corrupt a score. Counting each solved challenge once, and removing duplicate level IDs, prevents double counting.
  • Client-side data is not cheat-proof, because the game itself writes the score.
  • Small configuration errors, such as a duplicated line in manifest.json, can stop the whole project from loading packages.

Limitations and next steps. The maps and gameplay are still in progress. The Login and Registration system and an administrator account that can change the coding questions are planned and not implemented. Network-failure behaviour and a standalone build still need testing.
