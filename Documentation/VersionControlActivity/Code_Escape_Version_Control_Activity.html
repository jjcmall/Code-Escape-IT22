Part II. Repository and Project Organization

Which project files are version controlled?

  • Assets/: scripts, scenes, prefabs, art, audio, fonts, data and every .meta file. The .meta files hold the asset IDs, so they must be committed or references break for the other members.
  • ProjectSettings/ and Packages/manifest.json + packages-lock.json: the engine settings and package versions, so every member opens the same project.
  • Documentation/ and README.md.
  • Unity is set to Force Text serialization (m_SerializationMode: 2), so scenes and prefabs are text (YAML) and Git can show and merge differences.

Which generated files are excluded?

Library/ (Unity's import cache), Temp/, Logs/, obj/, Build/, UserSettings/ (per-user editor layout), generated *.csproj and *.sln, and *.log. They are rebuilt on each computer, and committing them would cause constant conflicts.

How are large assets handled?

The largest tracked file is Assets/Animations/Sam/Sam.fbx (32.7 MB), then a 17.2 MB and a 9.4 MB texture for the same character. No file is over 50 MB, so plain Git is used. .gitattributes only has * text=auto (line-ending normalisation). Decision: Git LFS is not needed now. If a model, audio or video file approaches 50 MB (GitHub warns at 50 MB and blocks at 100 MB), the group will add it to Git LFS before committing it.

How does another member obtain a usable copy?

  1. Install Unity Editor 6000.5.10f1 through Unity Hub.
  2. In GitHub Desktop, choose File > Clone repository, pick Code-Escape-IT22 and clone it (or use Unity Hub: Add > Add project from repository > GitHub).
  3. In Unity Hub choose Add > Add project from disk and select the cloned folder. The first open is slow because Unity rebuilds Library/.
  4. Sign in to Unity with the group's agreed account if cloud features need to be tested (see Documentation/CloudSave.md).

Part VII. Merge Conflict and Game-Asset Collaboration

Example from our own project: two members change Assets/Scripts/Cloud/CloudProgressService.cs in different branches. One adds the username and password sign-in (feature/cloud-accounts); the other moves the record-building code into ProgressRecordBuilder (refactor/save-progress). Both edit the same file, and the second one to merge sees a conflict.

1. What could cause the conflict? Two branches changed the same lines (or neighbouring lines) of the same script, or both changed the same scene or prefab, for example 00_MainMenu.unity. It also happens when a member keeps working from an old main for days.

2. How does Git and GitHub identify or prevent it? Git cannot merge overlapping changes by itself. GitHub shows "This branch has conflicts that must be resolved" on the pull request, and GitHub Desktop lists the conflicted files and marks them with <<<<<<<, =======, >>>>>>>. We reduce the risk by keeping branches small and short, updating from main before starting and before opening a pull request, and telling the group before editing a scene or prefab (only one member edits a given scene at a time).

3. How should the team resolve it?

  • Talk first: both versions may be valid work, so the two developers decide together.
  • Update the branch from main. In the conflicted script, keep both changes and remove the conflict markers. For a scene or prefab, keep one version and redo the other member's edit in the Unity editor, because merged YAML can be invalid.
  • Commit the merge, push, and ask the reviewer to check the resolved file.

4. What should be tested after resolution? Unity opens the project and the Console has no compile errors; the project plays from the main menu; both features still work (sign in and save, and the refactored save path); and the pull request diff contains only the intended files.

Game assets. Scenes and prefabs are saved as text, which helps, but they still conflict easily. Rules: one member owns a scene or prefab at a time; models, textures and audio are binary, so they cannot be merged and the later version simply replaces the earlier one. For those files, tell the group before replacing one, and use Git LFS if a file grows toward 50 MB. Git does not have file locking by default, so the agreement between members acts as the lock.

Part VIII. Team Collaborative Workflow

Before starting development

Fetch origin and pull the latest main
-> confirm the assigned task with the group
-> create a branch from main (Branch > New branch, name feature/... or fix/...)

During development

Make a small change
-> test in Unity (Console has no errors, the feature works)
-> commit with a meaningful message (what and why), under your own account
-> push the branch to GitHub often (Publish branch, then Push origin)
-> update from main when others have merged

Before integration

Finish the task and test it
-> open a Pull Request with the template (what, why, component, how tested)
-> a different member reviews with the checklist
-> developer fixes issues with new commits if changes are requested

After approval

Merge the Pull Request on GitHub (a merge commit, so each member's commits stay visible)
-> delete the branch
-> everyone fetches and pulls the new main
-> one member tests the integrated project in Unity
-> continue with the next task

Team rules

  • No direct commits to main. The group turns on branch protection in GitHub (Settings > Branches > Add rule for main: require a pull request and at least 1 approval).
  • One branch per task, merged within a few days.
  • Do not commit Library/, Temp/, Logs/ or UserSettings/ (already ignored). Do not commit passwords, keys or tokens.
  • Commit messages say what changed. Avoid "update", "final", "done" or "test".
  • Announce in the group chat before editing a scene, a prefab or a large asset.
