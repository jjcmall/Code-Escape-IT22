Part I. Final System Architecture

Code Escape is a Unity PC game. Gameplay runs entirely in the game client. Progress is saved locally and copied to Unity Cloud Save, which is the only external service. The group does not use its own backend, API, SQL or Firebase database. A Login and Registration system is planned and will be implemented soon; it is not implemented yet, and the game currently signs the player in anonymously with no login screen. An administrator account that can change the coding questions is also planned; it depends on the login system and is not implemented.

Architecture explanation

Overall structure. A single Unity PC client contains the user interface, the game logic and the persistence layer. Unity Authentication and Unity Cloud Save are the only external services. The legend: the dashed rectangle is the system boundary, solid arrows are communication or data movement, and each box shows its implementation status.

User interaction. The student uses the keyboard and mouse on the Game UI (menus, level map, question panel) and moves the character with the Player Controller.

Main processing. It happens inside the client: obstacle contact opens a question, ProgrammingChallengeManager compares the answer with the stored solution (player code is never executed), updates the score, and the level managers unlock levels.

Persistent data. Progress is written to local storage (PlayerPrefs, JSON) and copied to Unity Cloud Save under the signed-in player. On start, the cloud copy is loaded and restored into the local save before gameplay is allowed.

Communication. Inside the client, components communicate through C# static events (ChallengeCompleted, ScoreChanged, LevelUnlocked, LevelCleared) and singleton Instance references. The client talks to the two Unity services through the Unity Gaming Services SDK over the internet.

External services. Unity Authentication (currently anonymous sign-in) and Unity Cloud Save (player-scoped key-value data). Not used: own backend or API, SQL or Firebase database. Planned: a Login and Registration UI that will feed the existing sign-in step, and an Admin Question Editor used by an administrator account to change the coding questions (both dashed in the diagram). Where edited questions will be stored is not decided yet; Unity Cloud Save Game Data (server-written custom items) is a candidate, and the game would then load questions from it instead of only from the bundled assets.

Part III. Data / Database Design

The project has no SQL or document database. Data is stored in two places: local storage (Unity PlayerPrefs, JSON strings) and Unity Cloud Save (player-scoped key-value items). Both store JSON text written with Unity's JsonUtility.

Storage structure

  CodeEscape.Progress                JSON  ProgressData
  CodeEscape.LevelProgress.python    JSON  LevelProgressData
  CodeEscape.LevelProgress.php       JSON  LevelProgressData
  CodeEscape.LevelProgress.sql       JSON  LevelProgressData
  CodeEscape.MusicVolume, SfxVolume, Fullscreen, ResolutionWidth/Height
  CodeEscape.SaveVersion             int
  CodeEscape.Cloud.Unsynced, CodeEscape.Cloud.PlayerId   (cloud bookkeeping)

UNITY CLOUD SAVE (per authenticated player, default access class)
  code_escape_progression            JSON  PlayerProgressData
  code_escape_snapshot               JSON  ProgressSnapshot
                                           |-- progress_json     = ProgressData as text
                                           '-- level_progress[]  = { language, json = LevelProgressData as text }

The cloud record is identified by the authenticated Unity Player ID: Cloud Save stores data under that player, so no shared key exists. Question content is not stored per player: it is 48 read-only ScriptableObject assets in Assets/ScriptableObjects/Questions.

Data integrity and validation

RuleHow it is enforced
A completed level appears only onceLevelProgressData.MarkCompleted and the cloud record use unique sets; Sanitize removes duplicates.
Level IDs must refer to existing levelsLevelProgressData.Sanitize drops unknown or empty IDs on load and before saving.
Score cannot be negative; counting twice is preventedScore is clamped at 0 (Mathf.Max) and computed from distinct solved and hinted IDs, so repeated events do not add points.
The record belongs to the signed-in playerplayer_id is set from the authenticated Player ID; Cloud Save stores data per player.
Both cloud keys must exist together; data must be readable and not from a newer versionIf only one key exists, JSON cannot be read, or the version is newer, the load fails with an error and nothing is overwritten.
Null or missing lists are repairedPlayerProgressData.Sanitize replaces null fields and lists.
Language must be valid (Python, PHP, SQL)ProgrammingLanguage.IsValid is checked before saving or loading progress by language.
Volumes stay between 0 and 1; resolution is both set or both 0SettingsData.Sanitize.
Only an administrator may change questions (Planned)Not implemented. The role must be checked by a server-side service, because the game client cannot be trusted.
An edited question stays valid (Planned)Not implemented. Rules to apply: unique question id, valid language, at least two choices with a valid correct index (or an accepted answer for typed questions).
Unchanged data is not re-savedA fingerprint of the record is compared with the last confirmed save before any cloud request.

Part IV. End-to-End Integration Design

Process 1: Save player progress

Player clears a level
 -> LevelManager / LevelProgressManager.RecordLevelCleared
 -> Local Save (level progress and playthrough written to PlayerPrefs)
 -> LevelCleared event -> Cloud Progress Service (RequestSave)
 -> Build record (PlayerProgressData + ProgressSnapshot), compare with last confirmed
 -> Unity Cloud Save (SaveAsync, two keys)
 -> Save confirmed
 -> Game UI: "Saved to cloud"
ItemDescription
TriggerA level is cleared. Also: level unlocked, score changed, challenge solved (batched after 3 seconds), main menu loaded, app paused.
Source ComponentLevel & Game State Manager (and Challenge & Scoring for score events)
Data Generated / SentPlayerProgressData JSON and ProgressSnapshot JSON (two Cloud Save keys)
Processing ComponentCloud Progress Service (builds the record, removes duplicates, computes the score, unlocks achievements)
DestinationUnity Cloud Save, under the signed-in player. The local save is written first.
Stored / Retrieved DataStored: current and highest unlocked level, completed levels, total score, achievements, timestamp, restore snapshot
Expected ResponseCloud Save confirms the write; the service marks the record as confirmed and clears the "unsynced" flag.
User OutputStatus chip: "Saving to cloud...", then "Saved to cloud" with the time. "Saved" is shown only after confirmation.
If it fails No internet or save error / timeout (20 s): the chip shows "Cloud save failed" with the reason and a Retry button; progress stays in the local save and is flagged unsynced; the game keeps running. Retry sends the full current state. On the next launch, unsynced local changes of the same player are sent again instead of being overwritten.
Data unchanged: no request is sent.
Invalid input: unknown level IDs are dropped and negative scores clamped before sending.

Planned change: when the Login and Registration UI is implemented, the sign-in step in Process 2 will use the student's registered account instead of an anonymous session. The rest of both flows stays the same.

Process 2: Load saved progress at startup

Game starts
 -> Cloud Progress Service
 -> Unity Gaming Services initialised
 -> Unity Authentication (anonymous sign-in) -> Player ID
 -> Unity Cloud Save (LoadAsync, two keys)
 -> Record found: restore into Local Save, managers, language and level map
    Record missing: create a new record from the current state and save it
 -> Game UI: gate removed, level map and progress panel show the data
ItemDescription
TriggerThe game opens (first scene loaded), or the player presses Retry on the connection screen.
Source ComponentCloud Progress Service
Data Generated / SentAnonymous sign-in request; load request for code_escape_progression and code_escape_snapshot
Processing ComponentUnity Authentication, Unity Cloud Save, then Cloud Progress Service and Local Save (restore)
DestinationLocal Save, Level & Game State Manager, Language Manager, Game UI
Stored / Retrieved DataRetrieved: the saved record and snapshot. Written locally: language, playthrough, level progress per language.
Expected ResponsePlayer ID obtained; record loaded and applied; state becomes Ready.
User Output"Connecting to Unity Cloud Save" screen, then the main menu. The level map shows saved unlocks and completions, and the Cloud progress panel shows the cloud data.
If it fails No internet or timeout: a full-screen "Cannot connect to Cloud Save" message with the reason and a Retry button; gameplay stays locked. Nothing is reset.
Record not found (new player): a new record is created and saved; the game unlocks only after the save is confirmed.
Only one key found, data unreadable, or newer version: an error is shown, the stored data is left untouched, and the player cannot start until it is resolved.
Project not linked or service disabled: initialisation error shown on the same screen.
