Architecture explanation (Part III)

The student interacts with the Unity PC client through keyboard and UI input: menu and level-map selection (MainMenuUI, LevelMapUI), movement (PlayerController) and answering questions in ChallengeUI. Main processing happens on the client, inside a persistent GameSystems object. ProgrammingChallengeManager compares answers with stored solutions, without executing player code, and updates the score, while LevelManager and LevelProgressManager unlock levels. Persistent data is stored on the student's own device in PlayerPrefs as JSON through SaveManager. No database, authentication or cloud service exists in the project. Components communicate through C# static events (such as ChallengeCompleted, ScoreChanged and LevelUnlocked) and singleton Instance references; ProgressSaveService listens to these events to autosave. File modification dates show that hazard-triggered challenges and the level map were edited most recently, so they appear to be the area under active work (the group should confirm). The next component to implement is student identity, meaning a Login/Registration UI backed by a storage interface, which Unity Authentication and Cloud Save would later depend on.

Evidence behind each point

  • Interaction: PlayerController.cs uses the Input System package; UI scripts under Assets/Scripts/UI.
  • Processing and communication: events declared in ProgrammingChallengeManager.cs, LevelManager.cs, ClueManager.cs, StoryManager.cs; subscribed in ProgressSaveService.cs (OnEnable).
  • Storage: SaveManager.cs calls only PlayerPrefs. A search of Assets/Scripts found no use of Unity Services, web requests, SQLite, Firebase, file I/O, login or registration.
  • Current / next work: inference from file timestamps (10 Oct 2026) and from the absence of any identity code. It is not a statement from the group.

Part IV — Data and Storage Alignment 5 points

Honest summary: the project has no database. The only implemented storage is Unity PlayerPrefs on the local computer (on Windows standalone builds Unity keeps PlayerPrefs in the current user's registry). All other storage below is Planned.

Gaps found in the current storage design. (1) Every user of one computer account shares the same save slot. (2) Finishing the story calls ClearSave(), so the final score and results are not kept after the Results screen. (3) Score is one running total with no per-level or per-question score history.

Part VI — Next Technical Milestone 4 points

Rubric focus: one milestone chosen from the real gap, with the gap, the milestone, the reason and the expected output.
Current GapProgress is saved only on the local computer and is not tied to any student. SaveManager is a static class that calls PlayerPrefs directly, so it cannot be replaced by a different storage without editing every caller. There is no Login/Registration UI, no student identifier, and no service package in manifest.json. In addition, the save and load path has not been verified at runtime, and finishing the story deletes the saved result.
Next Technical MilestoneStudent identity and a swappable progress store, verified locally.
  • Add a small storage interface (for example IProgressStore) with the current PlayerPrefs code as its first implementation.
  • Introduce a studentId and key every saved record by it, with a minimal Login/Registration scene that produces the ID (a local ID first).
  • Run and record a save, quit, relaunch, continue test for R3 and R5.
ReasonUnity Authentication and Cloud Save both depend on having a student ID and on a storage layer that can change backend. Adding either service before those two pieces would mean rewriting the save code twice. The milestone adds no new technology, it uses the existing, already coded save system, and it closes the verification gap shown in E1 and E7. It also tests whether the group really needs accounts before spending effort on cloud services.
Expected Output
  • Source: the interface, the PlayerPrefs implementation, and a Login/Registration scene with its script.
  • Save data keyed by studentId; two different IDs on one computer keep separate progress.
  • Evidence for the next report: screenshots of the login scene and of the Continue flow, a Console log of save and load, and a short written test table (steps and observed results).
  • An updated Part III diagram with the Login UI marked Implemented and Unity Authentication/Cloud Save still Planned, or Implemented only if they are added later.

Assumption to confirm. This milestone assumes the capstone requires student accounts. If the group decides accounts are out of scope, the alternative milestone is the same runtime verification of the local save plus keeping the final score instead of clearing it in ResultsManager.
